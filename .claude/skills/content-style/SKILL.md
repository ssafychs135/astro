# 문체 점검 (content-style)

이 저장소의 한국어 콘텐츠(블로그·포트폴리오·UI 문구)를 `CONTENT_GUIDE.md`의 "문체 규칙"에 맞춰 점검하고 고친다.

## 절차

1. **대상 파일 결정.** 인자로 파일 경로가 오면 그 파일, 없으면 방금 작성·수정한 `src/content`의 `.md`/`.mdx`. 본문과 함께 frontmatter(`title`, `description`, `tags`), 글에 들어간 컴포넌트의 UI 문구와 `aria-label`, 원고를 만드는 생성 스크립트 안의 문자열(예: description)도 점검 대상에 넣는다. `lint.sh`와 `sentences.py`는 본문 파일만 보므로 이 문자열들은 직접 읽는다.
2. **기계 점검.**
   - `bash .claude/skills/content-style/lint.sh <파일>`을 실행한다. 정규식으로 잡히는 패턴(선언식 서두, 구어체)을 확인한다.
   - `python3 .claude/skills/content-style/sentences.py <파일>`로 글자 수가 많은 문장 25개를 뽑는다. 길이는 후보를 고르는 기준일 뿐이므로, 하나씩 읽고 규칙 5에 해당하는 문장만 고른다. 나열이라서 긴 문장은 그대로 둔다.
3. **판단 점검.** `CONTENT_GUIDE.md`의 "문체 규칙" 29개를 기준으로 본문을 직접 읽는다. 규칙마다 붙은 수정 예시를 확인한 뒤 판단한다. 정규식으로 못 잡는 다음 항목을 특히 본다.
   - 문장: 명사구나 연결어미로 끝난 문장, 생략된 주어·목적어·조사, 겹쳐 쓴 `~의`, 조사 없이 나열한 한자어, 주제어가 겹치거나 주어와 서술어가 어긋난 문장, 대상이 확정되지 않는 지시어와 짝을 잃은 접속어(`반면에`, `그래서`), 같은 대상을 다르게 부른 이름(표의 항목 이름 포함), 한 문단 안에서 섞인 시제, 소제목에 기대어 주어를 생략한 절 첫 문장
   - 표현: 일반 어휘를 대체한 비유, 과장된 부사, 의인화, 극적 표현, 엠대시(—) 연결, 정착된 번역어를 두고 쓴 원어
   - 글 구성: 선언식 서두, 글의 구조를 정당화하는 문장, 정보가 없는 방어적 caveat, 하지 않은 일이나 겪지 않은 문제를 적어 미리 방어하는 문장(하지 않은 것 자체가 판단의 근거나 결과이면 남긴다), 시간순으로 나열만 한 구성, 사건의 크기보다 큰 서술, 사건 뒤에 붙인 교훈 문장, 사실을 실수로 규정하거나 독자에게 지시하는 문장(`자주 하는 실수`, `~할 때는 ~한다`), 명사구가 아닌 소제목, 앞 편에서 설명한 개념을 다시 설명하는 문장, 절 첫 문장의 결론을 되풀이하는 문장, 뒤에 나올 표나 사실을 예고만 하는 문장, 여러 절과 편에 흩어진 환경·하드웨어·데이터 규모 같은 사실, 여러 항목에 똑같이 씌운 소절 틀(같은 제목 아래 서로 다른 내용), 문단을 빼거나 소절을 합친 뒤 생긴 중복
   - 주장과 사실: 관측 범위를 넘은 주장(확인하지 않은 것, 잰 적 없는 인과, 사례 하나에서 만든 기준), 해석어로 바꾼 측정값, 표본의 흔들림 안에 있는 차이를 단정한 표현, 사람의 판단과 대량 작업을 한 동작으로 묶은 서술, 도구나 협업자가 만든 결함을 고친 일을 글쓴이의 성과나 사례로 쓴 항목(누가 만들었는지 원자료에 없으면 글쓴이에게 확인), 조건이 다른 수치를 범위 없이 나란히 둔 곳, 본문보다 세게 단정하거나 채택과 폐기를 뒤바꾼 요약(description, 도입 문단, 절 첫 문장)
   - 그림, 수식, 코드 블록: 차원 표기만 있고 항의 뜻이 없는 수식, 한글이 섞인 줄을 공백으로 세로 정렬한 코드 블록(콜론, 화살표, 괄호 선), 본문을 되풀이하는 그림 아래 설명문과 반대로 그림의 출처를 밝히는 문장의 누락
   - 코드 블록, 코드 주석, 인용문의 문장은 문체 점검 대상에서 제외한다. 다만 코드 블록의 정렬 방식(규칙 28)은 보고, 정렬에 기대는 도식이 있으면 화면에서 확인한다.
4. **사실 대조.** 원자료(실험 기록, 원본 문서)가 있으면 본문의 수치, 단위, 셈의 단위(건과 행, 고유 개수와 복제 포함 개수, 개와 쌍, 측정·판독 결과는 `건`이고 구성 요소는 `개`인지, 편 사이에서 같은 자리에 같은 단위를 쓰는지), 이어지는 두 수치 사이의 중간 단계(빠진 값이 있으면 원자료에서 찾아 넣고, 원자료의 배수가 실제 값과 맞지 않으면 배수를 적지 않는다), 고유 명칭, 인용한 논문 이름을 하나씩 대조하고, 표와 바로 앞뒤 본문이 서로 어긋나지 않는지 본다. 표현 점검에서 모호하다고 짚은 문장은 사실 오류를 가리고 있을 수 있으므로 원자료로 확인한다. 원자료에 없는 수치는 만들지 않는다. 원자료에 무효나 오염으로 적힌 측정은 다시 잰 값이 없으면 결과로 인용하지 않는다.
5. **수정.** 발견한 항목을 고친다. 사실과 구조는 유지하고, 생략된 성분을 채우거나 비유를 일반 어휘로 바꾸는 방식으로 표현만 고친다.
   - 원고를 원본 문서에서 스크립트로 옮겨 만든다면 발행본이 아니라 원본 문서를 고친다. 고친 뒤 스크립트를 다시 돌리고, 스크립트가 컴포넌트 삽입 위치로 찾는 기준 문구가 여전히 원고에 있는지, 스크립트가 원고의 일부를 덮어쓰고 있지 않은지 확인한다.
   - 이름이나 설명을 하나 고치면 같은 낱말로 문서 전체(표, 코드 블록, 컴포넌트 문구 포함)를 검색해서 옛 표현이 남은 자리를 함께 고친다(규칙 6).
   - 문장을 빼기 전에 그 문장에만 들어 있는 사실(측정 조건, 대상, 횟수, 근거)이 있는지 본다. 있으면 남는 문장으로 옮긴다(규칙 14, 20).
   - 문단을 빼거나, 소절을 합치거나, 소제목을 없앤 뒤에는 앞뒤 문장의 지시어, 주어, 중복을 다시 읽는다(규칙 3, 7, 18).
   - 그림 아래 설명문을 뺄 때는 본문과 한 문장씩 대조하고, 본문에 없는 내용은 지우기 전에 보고한다(규칙 29).
   - 배포 직전 검토이거나 다른 사람과 나누어 검토하는 중이면, 명백한 오탈자만 바로 고치고 문장을 나누거나 표현을 바꾸는 항목은 위치, 현재 문장, 문제, 제안 문장을 적은 목록으로 먼저 보고한다.
6. **보고.** 무엇을 왜 고쳤는지 알린다. 고치지 않고 남긴 항목이 있으면 그 이유도 적는다.
7. **규칙 갱신.** 수정이 끝날 때마다 그 수정이 다음 글에서도 반복될 유형인지 판단한다. 반복될 유형이면 `CONTENT_GUIDE.md`의 규칙(예시 포함)이나 이 스킬의 점검 항목에 넣고, 이미 있는 규칙이면 예시만 보탠다. 보고에는 무엇을 넣었는지, 또는 넣을 것이 없었는지를 적는다.

규칙의 정본은 `CONTENT_GUIDE.md`다. 문장 규칙은 fluent-korean 출력 스타일을 기준으로 삼으며, 목표는 의미가 명확하고 구조가 안정적인 한국어 문장이다. 애니메이션 컴포넌트를 넣은 글은 `CONTENT_GUIDE.md`의 "애니메이션 컴포넌트 검수"도 따른다.
