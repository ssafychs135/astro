WWDC 2026에서 애플은 언어 모델 두 개를 함께 공개했다. 하나는 클라우드에서 도는 1.2조 파라미터 규모의 모델이고, 다른 하나는 아이폰에서 직접 도는 온디바이스 모델 AFM 3 Core Advanced다. 둘 다 <Term word="MoE" def="Mixture-of-Experts. 모델을 여러 개의 전문가(expert) 블록으로 나누고, 입력마다 그중 일부만 활성화해 계산량을 줄이는 희소 활성 구조." /> 구조지만 전문가를 고르는 방식이 정반대다. 클라우드 모델은 업계 표준대로 토큰마다 전문가를 고르고, 온디바이스 모델은 프롬프트 한 번에 전문가를 고른다.

이 차이는 알고리즘 선택이 아니라 하드웨어에서 비롯된다. 아이폰의 메모리 대역폭이 표준 방식을 허용하지 않았고, 애플은 그 제약에 맞춰 라우팅 방식을 바꿨다. 20B 규모의 모델을 아이폰에 담았다는 말의 실제 의미는 여기에 있다.

## 표준 MoE에는 숨은 전제가 있다

MoE는 모델의 <Term word="FFN" def="Feed-Forward Network. 트랜스포머 각 층에서 어텐션 뒤에 붙는 완전연결 블록. 전체 파라미터의 큰 비중을 차지하며, MoE는 이 블록을 여러 전문가로 쪼갠다." /> 블록을 여러 전문가로 쪼갠 뒤, 입력마다 라우터가 상위 몇 개의 전문가만 골라 계산한다. 전체 파라미터는 크지만 한 번의 추론에 쓰이는 파라미터는 일부에 그친다. 규모는 키우면서 계산량은 억제하는 방식이다.

대표적인 예가 DeepSeek-V3다. 총 671B 파라미터를 갖지만 토큰 하나를 처리할 때 활성화되는 것은 약 37B다. 각 MoE 층은 상시 활성인 shared expert 1개와 routed expert 256개로 구성되고, 토큰마다 그중 8개가 선택된다. 토큰이 바뀔 때마다 선택되는 전문가 조합이 달라진다.

여기에 겉으로 드러나지 않는 전제가 하나 있다. **모든 전문가의 가중치가 빠른 메모리에 상주해야 한다**는 것이다. 어떤 토큰이 어떤 전문가로 갈지는 그 토큰을 계산해봐야 알 수 있으므로, 라우터가 무엇을 고르든 즉시 접근할 수 있어야 한다. 데이터센터 GPU는 이 전제를 <Term word="HBM" def="High Bandwidth Memory. 데이터센터 GPU에 붙는 고대역폭 메모리. 초당 수 TB의 대역폭을 제공해 토큰마다 전문가를 바꿔도 병목이 생기지 않는다." />로 충족한다. 671B 전체를 고대역폭 메모리에 올려두고, 토큰마다 다른 전문가 8개를 부담 없이 읽는다.

## 아이폰에서는 이 전제가 깨진다

아이폰의 메모리 환경은 데이터센터와 다르다. 통합 메모리(DRAM) 용량이 제한적이라 20B 모델 전체를 상주시킬 수 없다. 그래서 애플은 모델 전체를 <Term word="NAND 플래시" def="아이폰의 저장 장치. 용량은 크지만 DRAM으로 데이터를 옮기는 대역폭이 HBM에 비해 크게 낮아, 매 토큰마다 가중치를 옮겨오기에는 느리다." />에 저장하고 추론에 필요한 부분만 DRAM으로 올리는 구조를 택한다.

문제는 NAND에서 DRAM으로 데이터를 옮기는 대역폭이 느리다는 점이다. 표준 MoE처럼 토큰마다 전문가를 바꾸면, 매 토큰마다 플래시에서 새 전문가 가중치를 읽어와야 한다. 이 로드가 생성 속도의 병목이 된다. 토큰 단위 라우팅은 고대역폭 메모리를 전제로 설계된 방식이고, 그 전제가 없는 아이폰에서는 성립하지 않는다.

정리하면 제약은 연산량이 아니라 메모리다. 20B를 아이폰에 올리는 일의 어려움은 계산이 무거워서가 아니라, 필요한 가중치를 제때 메모리로 가져오지 못해서 생긴다.

## 애플의 해답: 전문가를 프롬프트 단위로 고른다

AFM 3 Core Advanced는 라우팅의 주기를 토큰에서 프롬프트로 옮긴다. 바탕이 된 기법은 애플 연구진이 제안한 <Term word="Instruction-Following Pruning" def="명령을 따르는 가지치기. 사용자 프롬프트를 읽고 그에 맞춰 매번 다르게 모델 일부를 잘라내는 동적 프루닝 기법. 정적으로 한 번 자르는 기존 프루닝과 달리 입력마다 남기는 부분이 바뀐다." />(IFP)이다.

이름을 풀면 명령을 따르는 가지치기다. 프루닝은 모델에서 덜 중요한 가중치를 잘라내 크기를 줄이는 기법이다. 기존 프루닝은 한 번 잘라 그 상태로 고정하지만, IFP는 입력된 명령에 따라 매번 다르게 잘라낸다. 정적 압축이 아니라 프롬프트에 맞춰 필요한 부분만 그때그때 남기는 동적 프루닝이다. 입력마다 남기는 부분이 달라진다는 이 성질이 곧 프롬프트 단위 라우팅과 같은 말이 된다.

핵심은 작은 예측기다. 이 예측기가 사용자의 프롬프트를 먼저 읽고, FFN 행렬에서 어떤 행과 열을 활성화할지 한 번에 결정한다. 결정된 전문가 집합만 플래시에서 DRAM으로 올린 뒤, 그 프롬프트의 생성 내내 재사용한다. 생성 도중 필요에 따라 주기적으로 다시 선택하기는 하지만, 토큰마다 바꾸지는 않는다. 플래시에서 DRAM으로의 로드 횟수가 크게 줄어든다.

전문가는 두 종류로 나뉜다. 항상 활성인 shared expert와, 프롬프트에 따라 선택되는 routed expert다. routed expert는 필요할 때만 DRAM으로 적재된다. 이 방식으로 20B 중 실제로는 1~4B만 메모리에 올라간다.

이 구조를 두고 애플은 활성 3B 설정에서 같은 크기의 dense 모델보다 수학과 코딩에서 5~8점 높았고, 9B dense 모델과 비슷한 성능을 냈다고 밝혔다. IFP 논문도 9B 모델을 입력마다 3B로 잘라내면 dense 3B보다 크게 앞서고 dense 9B에 근접하면서, 추론 지연은 3B 수준을 유지한다고 보고한다. 프롬프트 단위 라우팅이 품질을 크게 희생하지 않으면서 메모리 문제를 우회했다는 주장이다.

## 두 번째 절약 장치: LoRA 어댑터

IFP가 20B 중 어떤 가중치를 켤지 정하는 장치라면, <Term word="LoRA" def="Low-Rank Adaptation. 기본 모델의 가중치는 고정한 채, 각 층에 작은 저계수 행렬을 덧붙여 특정 작업에 맞게 조정하는 미세조정 기법. 어댑터 크기가 작아 교체·배포가 가볍다." /> 어댑터는 그 위에서 모델을 무엇에 특화할지 정하는 별개의 장치다. 하나는 메모리에 올릴 파라미터를 줄이고, 다른 하나는 기능마다 모델을 따로 두지 않게 한다. 목적이 다르다.

애플의 온디바이스 전략은 기본 모델 하나를 고정해두고, 요약·메일·알림 같은 기능별로 작은 LoRA 어댑터만 갈아 끼우는 방식이다. 어댑터는 모델 여러 층에 꽂히는 작은 모듈이고, 기능이 바뀌면 이 모듈만 교체한다. 기능마다 20B 모델을 통째로 복제하면 저장 공간이 감당되지 않지만, 어댑터는 그보다 훨씬 작아 하나의 기본 모델에 여러 특화를 붙일 수 있다. 개발자도 Foundation Models 프레임워크로 자체 어댑터를 학습해 붙일 수 있고, 어댑터는 앱과 함께 배포하거나 서버에서 내려받는 식으로 관리한다.

정리하면 애플은 메모리를 두 겹으로 아낀다. IFP로 추론당 활성 파라미터를 줄이고, LoRA로 기능당 저장 비용을 줄인다. 20B 규모의 모델을 아이폰에서 실제로 굴리는 일은 이 둘을 합쳐야 성립한다.

## 노선 비교: 같은 MoE, 다른 선택 주기

토큰 단위 MoE와 프롬프트 단위 라우팅을 나란히 두면 차이가 분명해진다. 두 방식은 희소 활성이라는 발상은 공유하지만, 라우팅 주기와 그것이 요구하는 하드웨어가 다르다.

| 항목 | 애플 온디바이스 (IFP) | DeepSeek·Gemini 계열 (토큰 MoE) |
|---|---|---|
| **라우팅 주기** | 프롬프트당 한 번 | 토큰마다 |
| **가중치 위치** | NAND 플래시 + 필요분만 DRAM | 전체를 HBM에 상주 |
| **대역폭 가정** | 낮은 NAND→DRAM 대역폭 전제 | 높은 HBM 대역폭 전제 |
| **총·활성 파라미터** | 20B / 1~4B | 671B / 37B (DeepSeek-V3 기준) |
| **전문가 구성** | shared + routed, 프롬프트로 선택 | shared + routed, 토큰으로 선택 |
| **강점** | 제한된 메모리에서 큰 모델 활용 | 토큰마다 최적 전문가 선택 |
| **약점** | 프롬프트 내 전문가 고정 | 모든 전문가 상주 필요 |
| **맞는 환경** | 아이폰 등 온디바이스 | 데이터센터 GPU |

두 방식 모두 활성 비율은 낮다. DeepSeek-V3는 671B 중 37B, 애플 온디바이스는 20B 중 1~4B만 쓴다. 차이는 활성 비율이 아니라 **전문가를 얼마나 자주 바꾸느냐**에 있다. 토큰 단위 MoE는 매 토큰 최적의 전문가를 고르는 대신 전체를 빠른 메모리에 상주시켜야 하고, IFP는 상주 요구를 낮추는 대신 한 프롬프트 안에서는 전문가를 고정한다. 어느 쪽이 낫다기보다, 각자의 하드웨어에 맞는 선택이다.

## 같은 회사가 왜 반대로 갔나

애플이 두 노선을 동시에 택한 이유는 두 모델이 사는 환경이 다르기 때문이다. 클라우드 모델은 메모리 제약이 없으므로 토큰 단위 MoE로 성능을 최대한 끌어올릴 수 있다. 온디바이스 모델은 제약이 설계를 강제한다. 같은 회사가 상반된 구조를 고른 것은 일관성의 문제가 아니라, 하드웨어 조건이 다르면 최적의 라우팅도 달라진다는 사실을 그대로 보여준다.

애플은 새로운 Siri를 자체 클라우드 모델이 아니라 구글에서 라이선스한 커스텀 1.2조 파라미터 Gemini 모델로 구동한다고 밝혔다. 보도에 따르면 연간 약 10억 달러 규모의 계약이다. 이 모델은 토큰 단위 MoE 구조이며, 애플의 Private Cloud Compute 인프라 위에서 돈다. 개인 데이터가 구글에 노출되지 않도록 설계했다는 것이 애플의 설명이다. 온디바이스가 제약 안에서 자체 기술로 푸는 영역이라면, 클라우드는 제약이 없는 대신 외부 프런티어 모델을 빌려 채우는 영역이다. 두 노선은 역할을 나눠 하나의 전략을 이룬다.

## 정리

온디바이스 AI의 병목은 연산이 아니라 메모리다. 모델을 얼마나 크게 만드느냐보다, 필요한 가중치를 제때 빠른 메모리로 가져올 수 있느냐가 설계를 가른다. 애플의 답은 라우팅 주기를 토큰에서 프롬프트로 늦춰 플래시 로드를 줄이는 것이었다. 20B를 아이폰에 담았다는 결과의 실체는 더 큰 모델이 아니라 다른 라우팅 방식이다.

라우팅 주기는 하드웨어를 따른다. 데이터센터에서는 토큰마다 고르는 편이 유리하고, 아이폰에서는 프롬프트마다 고르는 편이 유리하다. 정식 테크리포트가 공개되면 이 구조의 세부와 성능 수치를 다시 확인할 수 있을 것이다.
