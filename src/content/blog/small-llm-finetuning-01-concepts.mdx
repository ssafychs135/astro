LLM을 내 데이터로 학습시킬 때 반드시 마주치는 용어들을 정리했다. base 모델, instruct 모델, SFT, LoRA, QLoRA, DoRA, DPO 일곱 가지이다.

## 전체 그림

미세조정이란 이미 학습된 모델을 내 목적에 맞게 조금 더 학습시키는 일이다. 순서대로 세 가지를 정해야 한다.

```
1. 무엇 위에 얹을 것인가 → base 모델 vs instruct 모델
2. 어떻게 학습시킬 것인가 → LoRA / QLoRA / DoRA (메모리를 아끼는 방법)
3. 무엇을 가르칠 것인가 → SFT (정답 따라 하기) 다음에 DPO (좋고 나쁨 구분하기)
```

2번과 3번은 서로 독립이다. "QLoRA로 SFT를 한다", "LoRA로 DPO를 한다" 처럼 조합해서 쓴다.

## 1. base 모델과 instruct 모델

**base 모델**은 글을 이어 쓸 줄만 아는 모델이고, **instruct 모델**은 거기에 "시키는 대로 하기"를 추가로 배운 모델이다.

### base 모델이 배운 것

인터넷에서 모은 글 수조 단어를 읽으면서 한 가지만 연습했다. **앞부분을 보고 다음 단어를 맞히는 일이다.**

```
입력: "오늘 점심은 김치"
정답: "찌개"
```

이것만 수천억 번 반복한 결과가 base 모델이다. 그래서 이 모델은 이어 쓰기만 할 줄 안다.

여기에 질문을 넣으면 어떻게 될까.

```
입력: "한국의 수도는 어디야?"
출력: "라고 물어보는 사람이 많은데요, 오늘은 그 이야기를 해보겠습니다."
```

답을 안 하고 질문 뒤에 올 법한 글을 이어 썼다. 잘못된 것이 아니라 배운 대로 한 것이다. 답처럼 보이는 출력이 나올 때도 있는데, 그것은 지시를 따른 것이 아니라 "질문 뒤에는 보통 답이 온다"는 통계를 따른 것이다.

### instruct 모델이 더 배운 것

base 모델에 두 가지 훈련을 추가한다.

1. "이런 지시에는 이렇게 답하라"는 예시 수십만 개를 보여 준다. (이것이 뒤에 나올 SFT다)
2. 답변 두 개를 놓고 "이쪽이 더 낫다"를 알려 준다. (이것이 뒤에 나올 DPO나 RLHF다)

그 결과 지시를 따르게 되고, 대화 형식이 정해진다. 모델 이름 뒤에 `-it` 나 `-Instruct` 가 붙어 있으면 이쪽이다.

대화 형식이 정해졌다는 말은 입력을 아무렇게나 넣으면 안 된다는 뜻이다. 학습할 때 이런 모양으로 배웠기 때문이다.

```
<사용자 차례> 한국의 수도는 어디야? <모델 차례> 서울입니다.
```

이 틀을 chat template이라고 부른다. 이 틀을 무시하고 원시 문자열을 넣으면 학습 때와 다른 상황이 되어 성능이 떨어진다.

### 고르는 기준

| | base | instruct |
|---|---|---|
| 문법 | 작은 모델에서는 문장이 깨지기도 한다 | 같은 크기에서도 깨지는 일이 드물다 |
| 입력 형식 | 자유롭다 | chat template에 맞춰야 한다 |
| 원래 말투 | 사전학습 코퍼스의 온갖 문체가 섞여 있다 | instruct 특유의 정중한 말투가 남는다 |
| 거부 | 없다 | 모델에 따라 "답변할 수 없습니다"가 나온다 |

**고르는 기준은 간단하다.** 만들려는 것이 대화나 질의응답이면 instruct를 쓴다. 출력 형식이 아주 특이하고 데이터가 아주 많으면 base를 검토해 볼 만하다.

> **이 프로젝트에서는**
>
> 사전학습 모델에 추가 학습을 하지 않은 채로 제목을 이어 쓰게 했더니 조사와 어미가 깨진 문장이 반복해서 나왔다. 문법이 깨지지 않을 때에는 여행 블로그나 게임 공략 위키 같은 다른 장르를 그대로 이어 썼다. 그래서 instruct 모델을 기반으로 골랐다. 이 과정은 2편에 적었다.

## 2. SFT (지도 미세조정)

**SFT는 정답을 보여 주고 그대로 따라 하게 만드는 학습이다.** 미세조정이라고 하면 보통 이것을 말한다.

### 동작 방식

입력과 정답을 짝지은 데이터를 준비한다. 아래의 입력과 정답은 설명을 위해 지어낸 예시이다.

```
입력: "키워드: 배달음식"
정답: "배달비 3천원 실화냐"
```

모델에게 이 정답을 보여 주고, 정답에 나온 단어들이 나올 확률을 높인다. 사전학습 때 하던 것과 똑같은 일인데, 데이터만 내 것으로 바꾼 것이다.

**여기서 중요한 한계가 하나 있다.** SFT는 "이 문장의 확률을 높여라"만 할 수 있다. "A가 B보다 낫다"는 말은 못 한다. 데이터에 들어간 예시는 전부 똑같이 옳은 것으로 취급된다. 이 한계 때문에 뒤에 DPO가 필요해진다.

### 손실을 거는 위치

실제 학습 데이터는 지시문과 정답이 한 덩어리로 들어간다.

```
지시문 (매번 똑같음): 다음 키워드로 게시판 제목을 만들어라. 키워드: 배달음식
정답: 배달비 3천원 실화냐
```

여기서 선택지가 생긴다.

- **전체에 손실을 걸면**: 모델이 지시문까지 생성하도록 배운다. 그런데 지시문은 매번 똑같으니 외우는 데 용량만 쓴다.
- **정답에만 손실을 걸면**: 지시문은 "조건"으로만 쓰이고 채점 대상이 아니다. 모델의 용량이 정답 쪽에 집중된다.

지시문이 고정되어 있으면 후자가 낫다. 라이브러리에서 `completion_only_loss=True` 같은 옵션으로 켠다.

### loss 숫자를 읽는 법

학습 중에 loss(손실) 값이 계속 찍힌다. 낮을수록 좋다고 알려져 있지만, **얼마나 낮아야 좋은지는 과제마다 다르다.**

이유는 이렇다. loss는 "다음에 올 단어를 얼마나 잘 맞혔나"인데, 애초에 맞힐 수 없는 자리가 있다. 예를 들어 "배달음식"이라는 키워드만 주고 제목을 쓰라고 하면 첫 단어는 무엇이든 될 수 있다. 원리적으로 예측이 불가능하다.

그래서 **다른 과제의 loss와 비교하는 것은 의미가 없다.** 같은 과제 안에서 설정을 바꿨을 때 값이 내려갔는지만 본다.

> **이 프로젝트에서는**
>
> loss 3.1 부근이 이 과제의 하한이었다. 첫 단어 하나에서만 7에서 9 정도가 나왔기 때문이다. 이 지점을 지나면 loss가 더 내려가도 생성물이 나아지지 않았다.

## 3. LoRA

**LoRA는 원래 가중치를 고정해 두고, 그 옆에 작은 우회로를 하나 만들어서 거기만 학습시키는 방법이다.** 모델 전체를 학습시킬 메모리가 없을 때 쓴다.

### 전체 미세조정의 메모리 비용

모델 전체를 학습시키려면 파라미터 하나마다 네 가지를 메모리에 들고 있어야 한다.

| 항목 | 크기 |
|---|---|
| 원래 값 | 2바이트 |
| 기울기 | 2바이트 |
| 옵티마이저 상태 두 개 | 8바이트 |
| 고정밀 사본 | 4바이트 |
| **합계** | **파라미터당 약 16바이트** |

2B 모델이면 20억 × 16바이트 = **32GB**다. 여기에 계산 중간값까지 더해야 한다. 16GB짜리 소비자용 GPU 한 장으로는 불가능하다.

### 우회로의 구조

중요한 것은 **입력이 두 경로로 동시에 들어간다**는 점이다. 원래 가중치를 지난 다음 우회로를 지나는 것이 아니다. 같은 입력이 양쪽으로 갈라져 들어가고, 두 결과를 더해서 출력한다.

<LoraFlow />

숫자는 이 프로젝트에서 실제로 학습한 모델의 어텐션 q_proj 값이다. 이 모델의 hidden size는 1536이고, q_proj는 1536차원을 2048차원으로 옮기는 행렬이다.

병렬 구조는 LoRA가 학습하는 대상에서 나온다. LoRA가 학습하는 것은 가중치 자체가 아니라 **가중치의 변화량** ΔW이다. 그런데 ΔW를 통째로 학습하면 W와 크기가 같아서 아낀 것이 없으므로, ΔW를 작은 행렬 두 개의 곱 `BA`로 근사한다. 두 행렬이 만나는 낮은 차원을 **rank**라고 부르며, 이 값이 우회로의 굵기를 정한다. 이제 출력을 계산해 보면 두 항으로 갈라진다.

```
h = (W + BA) x = Wx + BAx
```

여기서 `x`는 입력이고 `W`는 원본 모델의 가중치다. `Wx`가 원래 경로이고 `BAx`가 우회로다. A와 B 사이는 순차이지만 활성화 함수가 없으므로 `BA`는 결국 행렬 하나이다.

"원본 모델 위에 올린다"는 흔한 표현은 파일을 로드하는 순서나 가중치를 더하는 관계를 가리키는 말이며, 입력이 흐르는 경로는 병렬이다.

미세조정으로 바뀌는 양은 생각보다 단순하다. 새로운 능력을 만드는 것이 아니라 이미 있는 능력을 쓰는 방식만 조정하는 일이라서, 그 변화량을 작은 행렬 두 개의 곱으로 충분히 근사할 수 있다. q_proj 하나는 파라미터가 약 315만 개인데, 크기 32짜리 우회로는 114,688개로 3.65%이다.

학습이 끝나면 이 작은 행렬만 저장하면 된다. 이것을 **어댑터**라고 부른다. 파일 크기가 수십에서 수백 MB 정도라서 여러 개 만들어 두고 갈아 끼울 수 있다.

<details>
<summary>수식으로 보기</summary>

```
h = W x + (α/r) · B A x

x: 입력
W: 원본 모델의 가중치. 학습하지 않고 고정한다
A: 입력을 rank 차원으로 줄이는 행렬. 정규분포로 초기화한다
B: rank 차원을 출력 크기로 되돌리는 행렬. 0으로 초기화한다
r: rank. 우회로의 굵기
α: alpha. r과 함께 우회로 출력의 배율(α/r)을 정하는 값
h: 출력
```

`B`가 0이므로 학습을 시작하는 순간의 출력이 원래 모델과 완전히 같고, 여기서부터 서서히 벌어진다.

</details>

### 정해야 하는 값

| 값 | 무슨 뜻인가 | 어떻게 정하나 |
|---|---|---|
| **r** (rank) | 우회로의 굵기 | 8~64. 학습이 부족하면 올린다 |
| **alpha** | 우회로 출력의 배율을 정하는 값 | 보통 r의 2배 |
| **target modules** | 어디에 우회로를 달 것인가 | 어텐션 4개 + MLP 3개 전부가 기본 |
| **dropout** | 우회로에 거는 dropout | 데이터가 적으면 0.05 |

우회로의 출력에 실제로 곱해지는 배율은 `alpha ÷ r` 이다. rank를 32에서 64로 올리면서 alpha를 64에 그대로 두면 배율이 2에서 1로 떨어진다.

<RankAlpha />

> **이 프로젝트의 설정** rank 32 / alpha 64로 시작해서 rank 64 / alpha 128로 올렸다. 어텐션 4개와 MLP 3개 전부에 적용했다.

### 할 수 있는 것과 없는 것

지금까지 설명한 것은 가중치 하나에서 일어나는 일이다. 이 프로젝트에서는 같은 구조가 모델 전체의 205개 지점에 붙었고, 앞 층에서 조정된 결과가 뒤 층의 입력이 되므로 효과가 누적된다. 그래서 LoRA로 말투뿐 아니라 출력 형식 자체를 바꿀 수도 있고, 반대로 학습률이나 에포크를 과하게 주면 원본의 능력이 실제로 망가진다.

학습하는 동안 W는 바뀌지 않고, 변화량도 저차원으로 제한되어 있다. 전체 미세조정에서 기존 능력이 무너지는 문제가 LoRA에서 덜한 이유가 이것이다. 동시에 이것이 한계이기도 하다. LoRA는 W가 이미 할 줄 아는 것 중에서 **어느 쪽을 쓸지 고르게 만드는 방법**이며, W가 아예 못 하는 일을 새로 만들어 넣지는 못한다.

> **이 프로젝트에서** 말투는 어댑터로 바뀌었다. 그러나 낱말은 모두 실재하는데 문장이 결합되지 않는 실패는 rank를 32에서 64로 올려도 줄지 않았다. 원인이 어댑터의 용량인지는 확인하지 못했다.

### 병합

학습이 끝난 뒤 우회로를 원래 가중치에 합쳐 버릴 수 있다. 합치면 추론 속도가 원래 모델과 똑같아진다. 합치지 않으면 행렬 곱이 조금 늘어난다.

이렇게 병합할 수 있는 것은 `W`와 `BA`의 모양이 같아서 더하기만 하면 되기 때문이다. 흔히 "순차면 병합할 수 없다"고 설명하지만 이것은 정확하지 않다. 활성화 함수가 없는 순차 구조라면 `BAW`도 결국 행렬 하나이므로 접어서 병합할 수 있다. **병합을 막는 것은 순차 배치가 아니라 비선형이다.** 층 사이에 병목 모듈을 끼워 넣는 adapter tuning 방식의 어댑터는 병목 안에 활성화 함수가 있어서 접을 수 없고, 그래서 배포해도 추론 지연이 남는다.

## 4. QLoRA

**QLoRA는 LoRA에 "원래 모델을 4비트로 압축해서 올리기"를 추가한 방법이다.** 메모리가 더 줄어든다.

LoRA로 옵티마이저 부담은 없앴다. 그런데 원래 모델 자체는 여전히 메모리에 있어야 한다. 2B 모델을 2바이트 정밀도로 올리면 4GB다. 여기에 계산 중간값을 더하면 16GB 카드가 빠듯해진다.

그래서 원래 모델을 **4비트로 압축해서** 올린다. 2바이트가 0.5바이트가 되니 4GB가 1GB로 줄어든다. 계산할 때만 필요한 부분을 잠깐 원래 정밀도로 풀어서 쓰는데, 이 작업이 매번 붙으므로 조금 느려진다.

**압축되는 것은 원래 모델뿐이다.** 새로 다는 어댑터는 그대로 16비트다. 그래서 학습 자체는 안정적으로 진행된다.

### 세 가지 장치

압축하면 값의 정밀도가 떨어지고, 학습 도중에 메모리가 순간적으로 치솟기도 한다. 그래서 세 가지 장치를 쓴다.

**NF4 (4-bit NormalFloat)**
4비트로는 16가지 값만 표현할 수 있다. 이 16칸을 어디에 배치할지가 문제다. 균등하게 나누면 낭비가 크다. 신경망 가중치는 대부분 0 근처에 몰려 있고 극단값은 드물기 때문이다. NF4는 값이 몰려 있는 0 근처에 칸을 촘촘히 두고, 바깥쪽은 성기게 둔다. 같은 4비트로 정보를 더 많이 담는다.

<Nf4Levels />

**double quantization**
압축할 때 쓰는 보조 상수들이 있는데, 그것도 다시 압축한다. 파라미터당 0.4비트 정도를 더 아낀다.

**paged optimizer**
메모리가 순간적으로 모자라면 옵티마이저 상태를 CPU 메모리로 잠시 넘긴다. 메모리 부족으로 학습이 중단되는 대신 조금 느려지는 쪽을 택한다.

### 배포할 때 주의할 점

4비트로 압축된 모델에 어댑터를 합치면 정밀도가 두 번 깎인다. 원본 정밀도 모델에 합친 다음, 그것을 다시 압축하는 편이 낫다.

> **이 프로젝트에서는** NF4로 압축해서 학습했다. 학습 환경은 2편에 적었다.

## 5. DoRA

**DoRA는 LoRA의 개선판이다. 이 프로젝트에서는 2.85배 느린데 손실은 같아서 쓰지 않았다.**

LoRA는 전체 미세조정과 학습되는 모양이 다르다는 관찰이 있었다.

가중치를 두 가지로 나눠 볼 수 있다. **크기**(얼마나 센가)와 **방향**(어느 쪽을 향하는가)이다. 전체 미세조정을 하면 이 둘이 따로따로 변한다. 그런데 LoRA에서는 둘이 묶여서 같이 움직인다. 이 제약 때문에 표현력이 떨어진다는 것이 DoRA의 문제 의식이다.

DoRA는 가중치를 크기와 방향으로 명시적으로 분해한다. 그리고 **방향에만 LoRA를 적용하고, 크기는 별도의 값으로 자유롭게 학습한다.**

같은 rank에서 LoRA보다 표현력이 높고, 전체 미세조정에 가까운 학습 모양을 보인다고 보고되어 있다.

대신 매 스텝마다 방향을 다시 계산해야 한다. QLoRA와 같이 쓰면 압축을 푸는 작업까지 겹쳐서 비용이 커진다.

> **이 프로젝트에서는** 같은 조건으로 40스텝씩 돌려서 비교했고, 측정한 표와 판단 과정은 2편에 적었다.

## 6. DPO

**DPO는 "이 답이 저 답보다 낫다"를 가르치는 학습이다.** SFT로는 못 하는 일이다.

### SFT로는 못 하는 것

SFT는 데이터에 있는 문장의 확률을 높이는 일만 한다. 그래서 이런 것을 가르칠 수 없다.

```
키워드 "배달음식"으로 만든 제목 두 개

A (추천을 많이 받은 제목): "배달비 3천원 실화냐"
B (그렇지 않은 제목): "배달음식 시켰습니다"
```

SFT 데이터에 A만 넣으면 A의 확률은 올라간다. 하지만 "B보다 A가 낫다"는 정보는 어디에도 들어가지 않는다. 둘 다 넣으면 똑같이 옳은 것으로 배운다.

### 이전 방식 (RLHF)

기존 방법은 두 단계였다.

1. 선호 데이터로 **점수 매기는 모델**을 따로 학습시킨다.
2. 그 점수를 최대화하도록 강화학습으로 원래 모델을 훈련한다.

모델을 두 개 학습시켜야 하고, 강화학습이라 불안정하다.

### DPO의 방식

**점수 매기는 모델을 만들지 않고, 선호쌍만으로 바로 학습한다.**

수학적으로 이런 사실이 알려져 있다. "점수를 최대화하는 최적의 모델"과 "그 점수" 사이의 관계를 풀면, **점수를 모델의 확률만으로 표현할 수 있다.** 그래서 점수 모델을 따로 둘 필요가 없어진다.

실제로 하는 일은 이렇다. 좋은 답 A와 나쁜 답 B를 짝으로 주고, A의 확률이 B의 확률보다 상대적으로 더 높아지도록 학습시킨다.

여기서 기준점이 필요하다. **참조 모델**은 학습 시작 전의 모델을 복사해서 고정해 둔 것이다. "출발점에 비해 얼마나 움직였나"를 재는 데 쓴다. 참조 모델은 변하지 않으므로 확률을 미리 계산해 두면 학습이 빨라진다.

**β(베타)** 는 출발점에서 멀어지는 것을 얼마나 억제할지 정하는 계수다. 보통 0.1에서 0.5 사이를 쓴다.

<details>
<summary>수식으로 보기</summary>

```
보상: r(x,y) = β · log( π_θ(y|x) / π_ref(y|x) )
손실: L = -log σ( r(x, y_w) - r(x, y_l) )

x: 입력
y_w: 좋은 답 (chosen)
y_l: 나쁜 답 (rejected)
π_θ: 지금 학습하고 있는 모델
π_ref: 참조 모델. 학습 전 상태로 고정한다
β: 참조 모델에서 멀어지는 것을 억제하는 계수
σ: 시그모이드 함수
```

보상은 참조 모델 대비 확률이 얼마나 올랐는지를 나타내고, 손실은 좋은 답의 보상이 나쁜 답보다 높아질수록 작아진다.

</details>

### 학습 중에 봐야 하는 숫자

| 이름 | 무슨 뜻인가 | 주의할 점 |
|---|---|---|
| reward (보상) | 출발점 대비 확률이 얼마나 올랐나 | 절대 품질이 아니다. 변화량이다 |
| accuracy (정확도) | 좋은 답의 보상이 나쁜 답보다 높은 비율 | 0.5는 무작위로 고른 것과 같다. 높다고 좋은 것이 아니다 |
| margin (마진) | 두 보상의 차이 | 크다고 좋은 게 아니다 |
| **chosen logp** | **좋은 답의 확률** | **이게 내려가면 문제다** |

왜 앞의 세 개는 믿으면 안 되는지가 다음 항목이다.

### likelihood displacement (가장 주의할 현상)

DPO의 손실 함수는 **두 확률의 차이만** 본다. 여기서 문제가 생긴다.

목표는 A의 확률이 B보다 높아지게 만드는 것이다. 그런데 손실 함수는 아래 두 가지를 구분하지 못한다.

| | 좋은 답 A의 확률 | 나쁜 답 B의 확률 | 두 확률의 차이 | 손실 |
|---|---|---|---|---|
| 의도한 방식 | 올라간다 | 내려간다 | 벌어진다 | 줄어든다 |
| 실제로 일어날 수 있는 일 | 내려간다 | 더 많이 내려간다 | 벌어진다 | 줄어든다 |

좋은 답의 확률까지 같이 떨어지는데 손실은 줄어든다. 이것을 **likelihood displacement**라고 부른다.

여기서 끝이 아니다. **떨어진 확률은 사라지지 않는다.** 확률의 총합은 1이므로 어딘가로 옮겨 간다. 어디로 갈까. **벌점을 받지 않은 곳**으로 간다. 즉 학습 데이터의 선호쌍에 한 번도 등장하지 않은 출력 쪽이다.

그래서 이런 상황이 생긴다. 지표는 전부 좋아졌는데 생성물을 읽어 보면 나빠져 있다. 전에 없던 이상한 출력이 나온다.

**마진과 보상 정확도만 보고 판단하면 안 된다. chosen logp를 반드시 같이 본다.**

### RPO (해결 방법 하나)

DPO 손실에 **"좋은 답의 확률을 유지하라"는 항을 하나 더 붙인다.** 좋은 답의 확률이 떨어지면 이 항 때문에 손실이 커진다. 그러면 차이를 벌리는 방법이 "나쁜 쪽을 내리는 것" 하나만 남는다.

```
전체 손실 = DPO 손실 + λ × (좋은 답에 대한 SFT 손실)
```

`λ`는 1.0 근처에서 시작한다.

라이브러리에서 인자 이름이 버전마다 다르다. TRL 기준으로 예전에는 `rpo_alpha` 였고, 1.12에서는 `loss_type=["sigmoid","sft"]` 와 `loss_weights=[1.0, λ]` 로 지정한다.

### 남는 한계

RPO를 써도 근본적인 문제가 하나 남는다. **DPO에는 "나쁜 것에 벌점을 준다"는 신호만 있고, "원래 분포를 유지하라"는 신호는 없다.**

모델이 벌점을 받는 패턴을 버릴 때, 그 확률이 어디로 갈지는 아무도 정해 주지 않았다. 옮겨 간 곳이 하필 목표 분포 밖이면, 실패의 종류만 바뀌고 총량은 그대로다.

> **이 프로젝트에서는** 세 번 시도했고 깨진 문장의 총량은 한 번도 줄지 않았다. 회차별 설정과 로그확률의 변화는 3편에 적었다.

## 7. 정리: 상황별 선택

```
① 기반 모델 고르기
   대화나 질의응답을 만든다 → instruct
   base가 문장을 제대로 못 만든다 → instruct
   출력 형식이 특이하고 데이터가 많다 → base도 검토

② 메모리 아끼는 방법 고르기
   GPU 메모리가 충분하다 → 전체 미세조정
   부족하다 → LoRA
   더 부족하다 → QLoRA
   학습이 잘 안 된다 → rank와 alpha를 함께 올린다
   그래도 안 되면 → DoRA. 단 40스텝 돌려서 속도를 먼저 잰다

③ 무엇을 가르칠지 고르기
   "이렇게 답해라"만 필요하다 → SFT에서 끝낸다
   "이게 저것보다 낫다"가 필요하다 → SFT 후에 DPO
   DPO를 할 때는 → chosen logp를 감시하고 처음부터 RPO 항을 같이 건다
```

## 용어표

| 약어 | 정식 명칭 | 한 줄 정의 |
|---|---|---|
| base | pretrained model | 다음 단어 맞히기만 배운 모델 |
| it | instruction-tuned model | 지시 따르기를 추가로 배운 모델 |
| SFT | Supervised Fine-Tuning | 정답을 보여 주고 따라 하게 하는 학습 |
| LoRA | Low-Rank Adaptation | 원래 가중치는 고정하고 작은 우회로만 학습 |
| QLoRA | Quantized LoRA | 원래 모델을 4비트로 압축한 LoRA |
| DoRA | Weight-Decomposed LoRA | 가중치를 크기와 방향으로 분해한 LoRA |
| DPO | Direct Preference Optimization | 점수 모델 없이 선호쌍으로 바로 학습 |
| RPO | Iterative Reasoning Preference Optimization | DPO에 "좋은 답 유지" 항을 더한 것. TRL이 이 이름으로 부른다 |
| RLHF | Reinforcement Learning from Human Feedback | 점수 모델 + 강화학습으로 하는 정렬 |
| chat template | | instruct 모델의 정해진 대화 입력 형식 |
| 어댑터 | adapter | LoRA로 학습한 작은 행렬 파일 |
