챕터마다 제목 후보를 받는 단계가 있다. 챕터의 전사문을 언어 모델에 읽히고, 그 챕터에서 다룬 화제 이름을 목록으로 돌려받는다. 답의 형식은 JSON 스키마로 정해 두고, 제약 디코딩으로 모델이 그 형식에서 벗어나지 못하게 한다. 제약 디코딩은 모델이 스키마에 맞는 글자만 생성하도록 막는 방식이다.

이 스키마에 이유 칸을 더하자, 모델이 이유 한 줄만 쓰고 응답을 끝내기 시작했다. 생성한 토큰은 70개였고, 받아야 할 화제 목록은 비어 있었다.

## 처음 의심한 원인

처음에는 입력이 너무 길어 컨텍스트가 모자란 것으로 보았다. 그런데 13.8분짜리 챕터에서도, 136분짜리 챕터에서도 똑같은 일이 일어났다. 입력 길이와 상관없이 매번 이유 한 줄을 쓴 직후에 응답이 끝났으므로, 컨텍스트는 원인이 아니었다. 그래서 바로 전에 바꾼 스키마를 의심하고 칸의 순서를 바꿔 보았다.

## 스키마의 칸 순서

제약 디코딩은 지시문에 적은 순서가 아니라, 스키마에 적은 필수 칸의 순서대로 답을 생성한다. 이유 칸은 자유롭게 쓰는 문자열이고, 화제 목록은 배열이다. 이유 칸이 배열보다 앞에 있을 때, 모델은 이유 한 줄만 쓰고 답을 마쳐 버렸다.

아래는 칸 이름을 일반화해 줄인 두 스키마다. 앞의 것은 이유만 쓰고 끝나고, 뒤의 것은 두 칸을 모두 채운다.

```json
{
  "properties": {
    "reason": { "type": "string" },
    "topics": { "type": "array" }
  },
  "required": ["reason", "topics"]
}
```

```json
{
  "properties": {
    "topics": { "type": "array" },
    "reason": { "type": "string" }
  },
  "required": ["topics", "reason"]
}
```

배열 칸을 이유 칸 앞으로 옮기기만 했는데, 파일럿 방송 다섯의 49챕터를 모두 확인한 결과 화제 목록이 빈 챕터가 하나도 없었다.

## 판정의 이유 칸

같은 원리를 챕터 경계 판정에 적용했다. 이웃한 두 후보가 이어지는지를 예 또는 아니오로 묻는 판정에서는 이유 칸을 판정 칸 앞에 두어, 모델이 이유를 먼저 쓰고 판정을 나중에 쓰게 했다. 칸의 순서가 곧 생성 순서이므로, 지시문으로 순서를 따로 부탁하지 않아도 스키마가 순서를 정한다.
